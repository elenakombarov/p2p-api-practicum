# Approval and exposure

Design only. No test code until this table is approved.

Scope is `POST /invoices/{invoiceId}/approve` and `GET /vendors/{vendorId}/exposure`. Create, submit, receive, invoice create, match, and GET invoice appear only as setup or as a precondition. This document does not specify those calls. `docs/test-design/invoices.md` uses approve only as setup for a later read or a later match.

The api project already resets once before the suite (`tests/api/reset.setup.ts`). These rows do not call `POST /admin/reset`. Each row creates the records it reads and uses ids from its own responses. A row does not depend on execution order or on a record created by another row. The server keeps one shared in-memory store. Rule 6 rejects a repeated invoice number for the same vendor, so every `invoice_number` in this document is used by only one row. Rows that invoice seed vendor `vnd-001` use numbers that do not appear in the other test-design documents, because those documents invoice the same vendor in the same store. A row that creates a vendor sends a vendor name unique to that row.

Seed vendor `vnd-001` may already have approved invoices by the time a row runs, because the reset is once per suite and other rows approve invoices for that vendor. Rule 11 sums every approved invoice for the vendor. No row asserts a literal `open_ap_liability` or a literal `vendor_exposure`. The only literal `95.1` in an expected approve or exposure body is the worked ledger on APR-02. That row keeps `vendor_id` `vnd-001` and the worked purchase order, full receipt, invoice lines, and match. Exposure rows that need a known sum create their own vendor and compare `open_ap_liability` to `total_amount` values the API returned. No row multiplies quantity by unit price. No row adds `95.1` to another amount. `docs/QUESTIONS.md` C.1 is not an expected result.

Approve sends no body and no `Content-Type`, except APR-09. Exposure sends no body. Create, receive, and invoice create send `Content-Type: application/json` and a JSON body. Submit and match send no body and no `Content-Type`.

Two purchase-order bodies are reused below. They are the same bodies as `docs/test-design/invoices.md`.

The one-line body:

```json
{ "vendor_id": "vnd-001", "line_items": [{ "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 }] }
```

The worked example (`docs/API.md` Purchase orders). APR-02 sends this body with `vendor_id` `vnd-001`. A row that creates its own vendor does not reuse this body and does not expect `95.1`.

```json
{
  "vendor_id": "vnd-001",
  "line_items": [
    { "sku": "LUM-2X4-8", "description": "2x4 stud, 8 ft", "quantity": 10, "unit_price": 4.75 },
    { "sku": "CEM-30KG", "quantity": 4, "unit_price": 11.9 }
  ]
}
```

The curl receipt (`docs/API.md` Purchase orders):

```json
{ "items": [{ "sku": "LUM-2X4-8", "quantity": 10 }] }
```

The curl invoice (`docs/API.md` Invoices), with the `po_id` and `invoice_number` of the row that cites it:

```json
{ "po_id": "<PO_ID>", "invoice_number": "<number>", "line_items": [{ "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 }] }
```

A ready one-line PO means: create the one-line body, submit that id, then the curl receipt. Do not assert that purchase order's `status`. A full delivery may leave it `submitted` or `closed` (`docs/QUESTIONS.md` D.18). Rule 10 allows an invoice on either status.

A held partial PO means: create the one-line body, submit that id, then `{ "items": [{ "sku": "LUM-2X4-8", "quantity": 4 }] }`. That delivery does not finish the ordered quantity of 10, so the purchase order stays `submitted`.

The worked receipt is both ordered lines, at those ordered quantities. The worked match example shows `partial_receipt` false and `received_value` 95.1 after that full receipt. APR-02 is the only row that sends it.

```json
{ "items": [{ "sku": "LUM-2X4-8", "quantity": 10 }, { "sku": "CEM-30KG", "quantity": 4 }] }
```

The worked invoice lines (`docs/API.md` Invoices), with the `po_id` and `invoice_number` of APR-02:

```json
{
  "po_id": "<PO_ID>",
  "invoice_number": "APR-WORKED",
  "line_items": [
    { "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 },
    { "sku": "CEM-30KG", "quantity": 4, "unit_price": 11.9 }
  ]
}
```

Documented contract:

- `POST /invoices/{invoiceId}/approve` returns 200 and an `ApproveResult`. OpenAPI assigns 201 only to vendor create, purchase-order create, and invoice create. Approve is 200 (`docs/QUESTIONS.md` A.2). The call takes the path `invoiceId` and no body. It approves a matched invoice (rules 4 and 9), posts the ledger entry (rule 7), and includes the vendor's new exposure (rule 11) (`docs/API.md` Invoices).
- `ApproveResult` is `invoice_id`, `status` `approved` only, `gl_entry`, and `vendor_exposure` (a number, dollars rounded to cents). `gl_entry` is `debits`, `credits`, and `balanced`. Each line has `account` and `amount` (OpenAPI `ApproveResult`, `GlEntry`, `GlLine`).
- The worked approve example is one debit `{ "account": "5000 Materials Expense", "amount": 95.1 }`, one credit `{ "account": "2000 Accounts Payable", "amount": 95.1 }`, `balanced` true, and `vendor_exposure` 95.1 (`docs/API.md` Invoices). APR-02 expects those two ledger amounts. It does not expect `vendor_exposure` 95.1. That number in the example is the vendor's exposure for the worked session, and rule 11 also counts every other approved invoice already stored for `vnd-001`. EXP-03, EXP-04, EXP-06, and EXP-07 do not expect `95.1`. Their setups are not that worked session.
- Rule 7: every approval posts a balanced ledger entry, total debits equal total credits. Success rows expect `balanced` true and those two totals equal. `GlEntry.balanced` is a boolean in the schema, while the rule says the posted entry is balanced (`docs/QUESTIONS.md` A.8.9). These rows still expect `balanced` true. The worked example is the only row that expects the account names and the amount 95.1. Whether every approval is exactly one debit to `5000 Materials Expense` and one credit to `2000 Accounts Payable` is open (`docs/QUESTIONS.md` D.31, A.8.5, APR-12).
- Rule 4, `three_way_match_gate`: an invoice cannot be approved until it passed the 3-way match. OpenAPI approve 400 is "Not matched, or already approved." The approval gate for a `received` invoice is this rule (APR-06). Rule 10, `workflow_gate`, lists submit, receive, invoice create, and a later match of an approved invoice. It does not name approve, so these rows do not expect `workflow_gate` on approve.
- Rule 9, `duplicate_approval`: an invoice can be approved only once (APR-07). A second invoice is a different approval (APR-04).
- Rule 11, `vendor_exposure_math`: a vendor's exposure equals the sum of `total_amount` over that vendor's approved invoices. `open_ap_liability` is that sum (`docs/QUESTIONS.md` A.6). The approve prose calls the same idea `vendor_exposure`. Neither source states that the two fields are equal (`docs/QUESTIONS.md` A.8.12, D.33, C.3). C.3 is not an expected result. A sum in this document adds `total_amount` values the API returned. It does not multiply price by quantity.
- `gl_balance` and `vendor_exposure_math` have no documented rejection story (`docs/QUESTIONS.md` A.8.3, D.30). No row expects either name on a 400.
- A 400 body has `detail` and `rule`. A 404 body has `detail` and no `rule` (`docs/API.md` Errors). Exact `detail` text is not asserted (`docs/QUESTIONS.md` D.10). OpenAPI approve 404 is "Invoice not found." OpenAPI exposure 404 is "Vendor not found."
- `GET /vendors/{vendorId}/exposure` returns 200 and a `VendorExposure`: `vendor_id`, `open_ap_liability` (a number, dollars rounded to cents), and `approved_invoices` (an array of strings). The documented error is 404 for an unknown vendor. The worked exposure example is `vendor_id` `vnd-001`, `open_ap_liability` 95.1, and `approved_invoices` `["inv-1ad78dbb"]`. That amount is not copied onto these rows. A row that created the vendor expects the created id in `vendor_id`. Where that vendor has one approved invoice, `open_ap_liability` is that invoice's returned `total_amount`, and `approved_invoices` is that invoice id. That array shape is the example. The amount is the returned field, not `95.1`.
- What exposure returns when the vendor exists and has no approved invoices, the order of `approved_invoices`, and whether those strings are always invoice ids, are open (`docs/QUESTIONS.md` D.34, C.4). C.4 is not an expected result. One-invoice rows on a vendor created in the row still expect the array to be that invoice id, which is the shape of the worked example array.
- Exposure for inactive seed vendor `vnd-002` is open (`docs/QUESTIONS.md` D.35).

## Open questions

1. On a successful approve, is `gl_entry` always one debit to `5000 Materials Expense` and one credit to `2000 Accounts Payable`, and is `balanced` always true? Rule 7 already requires equal debit and credit totals. APR-02 expects that ledger shape, and the amount 95.1, only for the worked invoice. (D.31, A.8.5, A.8.9, APR-12)
2. Which requests, if any, return `rule` `gl_balance` or `vendor_exposure_math`? Both are success promises here. (D.30, A.8.3, APR-13, EXP-16)
3. Are `vendor_exposure` and `open_ap_liability` required to be equal? The written examples each show 95.1 for the worked session. This document does not copy that amount onto an exposure row, and it does not assert the two fields are equal. C.3 is not an expected result. (D.33, A.8.12, EXP-13)
4. What does exposure return when the vendor exists and has no approved invoices? C.4 is not an expected result. (D.34, EXP-04 before approval, EXP-11)
5. What is the order of `approved_invoices`, and are the strings always invoice ids? The one-invoice example expects that invoice id. Order is not asserted for two invoices. (D.34, EXP-05, EXP-12)
6. Is exposure for inactive seed vendor `vnd-002` HTTP 200? (D.35, EXP-10)
7. What is the formula for `Invoice.total_amount`? APR-05 and EXP-05 use the returned value as the rule 11 addend and do not predict it. C.1 is not an expected result. (D.20)
8. Is a purchase order `closed` in the same response as the delivery that finishes the last line? Ready one-line setups do not assert that status. (D.18)
9. If POST approve is sent with a JSON body, is that body rejected? (D.9, APR-09)
10. Are query parameters ignored? (D.7, APR-10, EXP-15)
11. What is returned for an empty or malformed `invoiceId` or `vendorId`? (D.8, APR-11, EXP-14)
12. Which rounding mode does "rounded to cents" use? (D.2, EXP-17)
13. Is `detail` free text? These rows assert that `detail` is present and do not compare its words. (D.10)
