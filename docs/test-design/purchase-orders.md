# Purchase orders

Design only. No test code until this table is approved.

Scope is `POST /purchase-orders`, `GET /purchase-orders/{poId}`, and `POST /purchase-orders/{poId}/submit`. `POST /purchase-orders/{poId}/receive` is not designed here. Rows that need a `closed` purchase order call receive only as setup, with a delivery quantity equal to the ordered quantity.

The api project already resets once before the suite (`tests/api/reset.setup.ts`). Ordinary rows do not call `POST /admin/reset`. Each row creates the records it reads and uses ids from its own responses. A row does not depend on execution order or on a record created by another row. Seed vendors `vnd-001` and `vnd-002` are the documented seed data. A row that creates a vendor sends a vendor name unique to that run. `POST /purchase-orders` rows send `Content-Type: application/json` and a JSON body, except POC-38. Submit rows send no body and no `Content-Type`, except SUBMIT-06. `GET` rows send no body.

Two request bodies are reused below.

The one-line body:

```json
{ "vendor_id": "vnd-001", "line_items": [{ "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 }] }
```

The worked example (`docs/API.md` Purchase orders):

```json
{
  "vendor_id": "vnd-001",
  "line_items": [
    { "sku": "LUM-2X4-8", "description": "2x4 stud, 8 ft", "quantity": 10, "unit_price": 4.75 },
    { "sku": "CEM-30KG", "quantity": 4, "unit_price": 11.9 }
  ]
}
```

Documented contract:

- `POST /purchase-orders` returns 201 and a `PurchaseOrder`. The operation creates a draft (`docs/API.md` Purchase orders; OpenAPI 201 "The new draft purchase order."). The `PurchaseOrder.status` enum also allows `submitted` and `closed`. These rows still expect `draft` on create and `submitted` on submit, which is what those operations say they do.
- The vendor must exist (404, description "Vendor not found.") and be active (400, rule `inactive_vendor_gate`). Seed `vnd-001` is active. Seed `vnd-002` is inactive (`docs/API.md` Seed data).
- Every line needs a `sku`, a `quantity` greater than 0 and at most 10,000, and a `unit_price` from 0 to 100,000. OpenAPI encodes that as `sku` `minLength` 1, `quantity` `exclusiveMinimum` 0 and `maximum` 10000, and `unit_price` `minimum` 0 and `maximum` 100000. `description` is optional and defaults to `""`.
- Invalid bodies are HTTP 400. `rule` is `validation_error` (`docs/API.md` Errors). The OpenAPI 400 text is "Invalid body or inactive vendor." Exact `detail` text is not asserted (`docs/QUESTIONS.md` D.10). The inactive-vendor sample sentences differ (`docs/QUESTIONS.md` A.8.1).
- A 404 body has `detail` and no `rule` (`docs/API.md` Errors; OpenAPI `Error.rule`).
- Each SKU may appear once per PO. The status and `rule` for a repeated SKU are open (`docs/QUESTIONS.md` D.13). An empty `line_items` array is open: OpenAPI sets `minItems` 1 and `docs/API.md` does not (`docs/QUESTIONS.md` D.14).
- The catalog is for reference. The purchase order carries its own `unit_price` (`docs/API.md` Catalog). Whether a `sku` must be one of the five catalog SKUs is open (`docs/QUESTIONS.md` D.11). Whether a description that differs from the catalog is stored is open (`docs/QUESTIONS.md` D.12).
- Server-created ids use the prefix `po-`. The pattern after that prefix is open (`docs/QUESTIONS.md` D.1). Assert only the prefix.
- The worked example documents `ordered_value` 95.1, `received_value` 0, `fully_received` false, `received_quantity` 0, and `description` `""` on the line that omitted it. Those values are asserted on POC-01. POGET-01 reads that same purchase order back. They are not asserted for any other create. An omitted `description` defaults to `""` on every create (OpenAPI `PoLineCreate.description`). Any other successful create expects HTTP 201, `status` `draft`, the `PurchaseOrder` required fields present, an `id` prefixed `po-`, `vendor_id` equal to the vendor sent, and the request property that row tests. It does not assert `ordered_value`, `received_value`, `fully_received`, or `received_quantity` (`docs/QUESTIONS.md` D.15).
- `GET /purchase-orders/{poId}` returns 200 and the same `PurchaseOrder` shape, or 404 "Purchase order not found."
- `POST /purchase-orders/{poId}/submit` returns 200 and moves a draft to `submitted`. Anything else is rejected with rule `workflow_gate` (rule 10). OpenAPI 400 is "The purchase order is not a draft." OpenAPI 404 is "Purchase order not found." Submit has no request body (`docs/QUESTIONS.md` A.2). SUBMIT-01 and POGET-02 expect `status` `submitted` on the id just created. They do not copy the worked example's totals or receipt fields onto the submitted purchase order.
- `POST /admin/reset` deletes every purchase order (`docs/API.md` System). A GET or submit of an id after that reset is documented, and it is deferred (POGET-06, SUBMIT-05). Those rows need an isolated server or a separate non-parallel run. They are not implemented in the current shared suite.
- Rules 2 through 9 and rule 11 are not rejections on these three operations. Rule 10 is applied here only as "submit only a draft."
