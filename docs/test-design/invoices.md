# Invoices

Design only. No test code until this table is approved.

Scope is `POST /invoices`, `GET /invoices/{invoiceId}`, and `POST /invoices/{invoiceId}/match`. `POST /invoices/{invoiceId}/approve` appears only as setup for an approved invoice. Create, submit, receive, and GET of a purchase order appear only as setup.

The api project already resets once before the suite (`tests/api/reset.setup.ts`). These rows do not call `POST /admin/reset`. Each row creates the records it reads and uses ids from its own responses. A row does not depend on execution order or on a record created by another row. The server keeps one shared in-memory store, and rule 6 rejects a repeated invoice number for the same vendor. Every `invoice_number` in this document is used by only one row, including numbers on requests that expect rejection. Seed vendor `vnd-001` is the active vendor from the documented seed data. A row that creates a vendor sends a vendor name unique to that row.

`POST /invoices` sends `Content-Type: application/json` and a JSON body, except INV-51. Match sends no body and no `Content-Type`, except MATCH-08. GET sends no body. Approve, when used as setup, sends no body and no `Content-Type`.

Two purchase-order bodies are reused below. They are the same bodies as `docs/test-design/purchase-orders.md`.

The one-line body:

```json
{ "vendor_id": "vnd-001", "line_items": [{ "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 }] }
```

The worked example (`docs/API.md` Purchase orders):

```json
{
  "vendor_id": "vnd-001",
  "line_items": [
    { "sku": "LUM-2X4-8", "description": "2x4 stud, 8 ft", "quantity": 10, "unit_price": 4.75 },
    { "sku": "CEM-30KG", "quantity": 4, "unit_price": 11.9 }
  ]
}
```

The curl receipt (`docs/API.md` Purchase orders):

```json
{ "items": [{ "sku": "LUM-2X4-8", "quantity": 10 }] }
```

The curl invoice (`docs/API.md` Invoices), with the `po_id` and `invoice_number` of the row that cites it:

```json
{ "po_id": "<PO_ID>", "invoice_number": "<number>", "line_items": [{ "sku": "LUM-2X4-8", "quantity": 10, "unit_price": 4.75 }] }
```

A ready one-line PO means: create the one-line body, submit that id, then the curl receipt. Do not assert that purchase order's `status`. A full delivery may leave it `submitted` or `closed` (`docs/QUESTIONS.md` D.18). Rule 10 allows an invoice on either status.

A held partial PO means: create the one-line body, submit that id, then `{ "items": [{ "sku": "LUM-2X4-8", "quantity": 4 }] }`. That delivery does not finish the ordered quantity of 10, so the purchase order stays `submitted`.

Documented contract:

- `POST /invoices` returns 201 and an `Invoice`. The prose fixes `status` `received`, `matched` `false`, and `partial_receipt` `null`. The 201 schema is the full `Invoice` enum (`docs/QUESTIONS.md` A.8.9). These rows still expect the prose values. `Invoice` requires `id`, `po_id`, `vendor_id`, `invoice_number`, `status`, `line_items`, `total_amount`, `matched`, and `partial_receipt`. `docs/API.md` does not name `vendor_id` or `total_amount` (`docs/QUESTIONS.md` A.8.4).
- Server-created invoice ids use the prefix `inv-`. The pattern after that prefix is open (`docs/QUESTIONS.md` D.1). Assert only the prefix.
- `InvoiceCreate` requires `po_id`, `invoice_number`, and `line_items`. `invoice_number` has `minLength` 1. `line_items` has `minItems` 1. Each line requires `sku` (`minLength` 1), `quantity` (`exclusiveMinimum` 0, `maximum` 10000), and `unit_price` (`minimum` 0, `maximum` 100000). The same quantity and price limits apply to invoice lines (`docs/API.md` Purchase orders). An invoice line has no `description`.
- Invalid bodies are HTTP 400. `rule` is `validation_error` (`docs/API.md` Errors). The OpenAPI 400 text is "Invalid body or a business rule rejected the invoice." Exact `detail` text is not asserted (`docs/QUESTIONS.md` D.10).
- A 404 body has `detail` and no `rule` (`docs/API.md` Errors). OpenAPI 404 on create is "Purchase order not found." OpenAPI 404 on GET and match is "Invoice not found."
- Rules 3, 6, 8, and 10 apply to create (`docs/API.md` Invoices). Rule 6 is `duplicate_invoice_detection`: the same vendor cannot use the same invoice number twice. Comparison ignores case and surrounding spaces, so `INV-7`, `inv-7`, and ` INV-7 ` are the same number. Uniqueness is per vendor (OpenAPI `POST /invoices` description, `docs/QUESTIONS.md` A.6).
- Rule 10 allows an invoice only on a submitted or closed purchase order. The documented rejection name is `workflow_gate`. Invoicing a draft is also a positive quantity against nothing received, so rule 3 applies to that same request. Which name is returned is open (INV-34).
- Rules 3 and 8 are named on create: `overpayment_protection` and `invoice_line_validation`. `docs/API.md` says the rule name is what a rejection shows. D.24 asks which status and `rule` are returned, because the OpenAPI 400 text does not map a name to each case. Those rows expect HTTP 400 and `detail`. They do not assert `rule`.
- Rule 3: everything invoiced on a purchase order never exceeds what was received, per line quantity and in total value. There is no tolerance. Whether a smaller quantity is allowed is open (`docs/QUESTIONS.md` D.22). Whether later invoices are added together is open (`docs/QUESTIONS.md` D.23). The value formula is open (`docs/QUESTIONS.md` D.20 and C.1). C.1 is not an expected result.
- Rule 8: every invoice line is for a SKU on the purchase order, and each SKU appears once.
- `GET /invoices/{invoiceId}` returns 200 and the `Invoice` with its current status. The schema has no `gl_entry` (`docs/QUESTIONS.md` D.32).
- `POST /invoices/{invoiceId}/match` returns 200 and a `MatchResult`. It runs the 3-way match and sets the partial-receipt flag (rule 5). `MatchResult` is `invoice_id`, `po_id`, `status` `matched` only, `matched` `true` only, `partial_receipt` boolean, `ordered_value`, `received_value`, `invoice_total`, and `message`. The worked example is the only documented `message`: "3-way match passed." The schema cannot represent a failed match (`docs/QUESTIONS.md` A.8.8 and D.28).
- Rule 5 sets `partial_receipt` to `true` when any line of the purchase order is not fully received. It is match output, not a documented rejection (`docs/QUESTIONS.md` A.8.3 and D.30).
- Rule 10 forbids matching an approved invoice again. OpenAPI match 400 is "The invoice is already approved."
- The worked match example's `ordered_value`, `received_value`, and `invoice_total` of 95.1 are asserted only on MATCH-01. They are not a formula, and they are not copied onto any other invoice or match. `total_amount` is not asserted on any invoice (`docs/QUESTIONS.md` D.20). Where `vendor_id` comes from is open (`docs/QUESTIONS.md` D.21). Do not assert its value. The field is still required to be present.
